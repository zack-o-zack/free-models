# Commit Messages

Releases are generated from commit messages (see [RELEASING.md](RELEASING.md)), so every commit
on `main` must follow [Conventional Commits](https://www.conventionalcommits.org/).

```text
<type>(<scope>): <description>

<body>

<footer>
```

## Type

| Type       | Use for                                          | Release |
| ---------- | ------------------------------------------------ | ------- |
| `feat`     | A new user-visible capability                    | minor   |
| `fix`      | A bug fix                                        | patch   |
| `perf`     | A performance improvement                        | patch   |
| `revert`   | Reverting an earlier commit                      | patch   |
| `refactor` | A code change with no behaviour change           | none    |
| `docs`     | Documentation only                               | none    |
| `test`     | Adding or changing tests only                    | none    |
| `style`    | Formatting only                                  | none    |
| `build`    | Build tooling and dependencies                   | none    |
| `ci`       | GitHub Actions and other CI configuration        | none    |
| `chore`    | Maintenance, including catalogue data updates    | none    |

Only `feat`, `fix`, `perf`, and `revert` appear in release notes. Choose the type by its effect
on users, not by the files touched: a dependency bump that fixes a vulnerability is `fix(deps)`.

## Scope

The scope is optional. Use the area the change affects: `web`, `json`, `catalogue`, `deps`, `ci`,
or a provider name such as `opencode`. Separate several scopes with a comma, for example
`feat(web,json): ...`.

The scope does not decide which package is released. A commit belongs to the json release when it
touches `packages/json`, and to the web release when it touches `apps/web`. Keep each commit
focused so that its message describes the change in every package it touches.

## Description

- Use the imperative mood: "add", "fix", "remove", not "added" or "adds".
- Start with a lowercase letter and do not end with a period.
- Keep the whole first line within 72 characters.
- Describe the change for a reader of the release notes, not the implementation steps.

## Body and Footer

- Use the body to explain why the change is needed when the description does not make it clear.
  Wrap lines at 72 characters.
- Mark a breaking change with `!` after the type or scope (`feat(json)!: ...`) and a
  `BREAKING CHANGE: <what changed and how to migrate>` footer.
- Reference issues in the footer, for example `Closes #123`.
- Do not add AI attribution, `Co-Authored-By` trailers for AI tools, or "generated by" notes.

## Pull Requests

Pull request titles use the same format. Squash merges use the title as the commit message, and
merge commits keep each branch commit, so every commit on the branch must follow these rules too.

## Examples

```text
feat(web): add side-by-side model comparison page
fix(catalogue): map heygen voice and qwen flash character offers
fix(deps): resolve security vulnerabilities in quality gate dependencies
chore: update free model catalogue
```

A breaking change:

```text
feat(json)!: move offer limits into a terms array

BREAKING CHANGE: `offer.limits` is now an object. Read the limit
strings from `offer.limits.terms`.
```
